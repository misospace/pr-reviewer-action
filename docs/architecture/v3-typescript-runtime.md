# ADR: v3 TypeScript runner boundary

Status: selected for the v3 migration (#670, parent #669). No production runtime change in this ticket.

## Current architecture

`action.yml -> composite steps -> Bash orchestration -> Python domain helpers`.
The manifest validates `gh`, `jq`, `curl`, `git`, `python3`, and `pgrep` before starting; serializes shared inputs into an owner-only file under `RUNNER_TEMP`; executes precheck, review, publish, and cleanup as separate composite steps. `scripts/run_review.sh` sources ordered sections, with `config.sh` setting defaults and `review.sh` writing `GITHUB_OUTPUT` and a best-effort `GITHUB_STEP_SUMMARY`. Review artifacts live in the checked-out workspace, while scripts are found through `github.action_path` / `GITHUB_ACTION_PATH`. `gating.sh` forks the CI and specialist branches, passes the CI subprocess an explicit `env -i` allowlist, walks the child tree with `pgrep -P` on abnormal exit, TERM/KILLs and waits for its leaders. This is required because killing the Bash wrapper alone has previously left network subprocesses alive. `platform_api.sh` routes host API calls to `gh` or `pr_reviewer/forgejo_backend.py` (`/api/v1`, PAT or runner OIDC JWT); GitHub-only GraphQL and Forgejo's missing check-runs API already have explicit degradation. Input/env serialization, state, traps, and platform differences are currently spread across shell, Python, and action metadata.

## Options and evidence

* **A: native JavaScript action**, `runs: {using: node24, main: dist/index.js}`. GitHub gives it a managed Node runtime and supports `post:` for post-job cleanup. Forgejo's [current action guide](https://forgejo.org/docs/latest/user/actions/actions/) documents `node20` actions, but does **not** establish `node24` support; Node actions also require Node in the runner's container image. A native-only v3 release would bet on an untested interpreter selector and lifecycle on Forgejo.
* **B: composite action with a one-step bundled Node CLI**. `shell: bash; run: node "$GITHUB_ACTION_PATH/dist/index.js"`, with `env` mapping kebab-case `inputs.*` to explicit CLI env names and `outputs.*.value` projecting step outputs. This is the contract used by production today, and [Forgejo's guide](https://forgejo.org/docs/latest/user/actions/actions/) documents composite actions and local action paths. The runtime still requires a suitable `node` executable in the job image; the wrapper must check it and fail with a useful version error. A composite's `if: always()` cleanup step can run after a failed main step, but it is not a substitute for in-process `finally` or signal/process-tree cleanup during a hard kill.

The isolated proof is `.github/workflows/v3-runtime-spike.yml` and `tests/fixtures/v3-runtime/`. **Real GitHub execution:** [workflow run 35882863567](https://github.com/misospace/pr-reviewer-action/actions/runs/35882863567), `ubuntu-latest`, 2026-09-23, checked-out commit `4ebf635a565a6ffa9a98929207145a4afab74320`. The job passed. Native `node24` and composite launcher both read `test-kebab-input=kebab-value`, resolved bundled `marker.txt` and checked-out `GITHUB_WORKSPACE`, parsed `GITHUB_EVENT_PATH` and `GITHUB_REPOSITORY` (workflow_dispatch identity `misospace/pr-reviewer-action`), fetched that repository with the workflow token via `getRepository`, ran `git rev-parse --show-toplevel` via argv (exit/stdout checked; stderr captured), wrote `test-kebab-output` consumed by a later expression (`native-passed` / `composite-passed`), appended a summary and wrote finalization markers. Runner logs show `mask probe: ***` after registering a non-sensitive canary via `::add-mask::`; the actual token is also registered, never printed. For the hung `sh -c 'sleep 90 & ...; wait'`, process-group TERM returned control and the checked grandchild PID no longer existed on this run. The composite failure probe intentionally threw; `steps.failure.outcome=failure` and its separate finalization marker existed. The composite runner `node` printed `v22.23.2` on this run. The fixture uses Node built-ins only and does not call any review/model endpoint.

**Forgejo was not executed.** No maintainer Forgejo runner exists; provisioning Forgejo and its runner solely for this one-off spike would be infrastructure work. [Forgejo v16.0.5 docs](https://forgejo.org/docs/latest/user/actions/github-actions/) explicitly favor familiarity over exact GitHub compatibility; [the action guide](https://forgejo.org/docs/latest/user/actions/actions/) lists composite and `node20` action types and notes runtime dependencies are not automatically installed. [The reference](https://forgejo.org/docs/latest/user/actions/reference/) describes kebab-case inputs, `GITHUB_*` aliases and context expressions; aliases do not prove every runner implementation behaves identically. Repository Forgejo REST compatibility is existing production code and fixtures, not runner execution evidence. `node --test tests/fixtures/v3-runtime/cli.test.mjs` checks that GitHub and Forgejo repository paths/auth headers are selected by an injected platform adapter without importing Octokit. Remain unverified: Forgejo's `node24` selector, composite `GITHUB_ACTION_PATH`/output/summary/secret-mask and failure-step behavior on a specific Forgejo runner version, and Node availability/version in a given runner image. Later migration CI or release qualification should execute the fixture on a disposable or maintainer Forgejo runner when available, and test OIDC JWT if using authorized integration.

## Decision

**Select B: composite compatibility wrapper + bundled Node CLI.** The real GitHub run proved both options, but Forgejo JavaScript-action `node24` support is not established. Composite is the already-working production runner contract and keeps the launcher trivial; TypeScript owns application orchestration, state, and domain logic. Native Node lost on cross-platform confidence, not GitHub functionality. Keep the action metadata composite until a separately evidenced cross-platform change.

## Lifecycle and platform boundary

Node `child_process.spawn(file, argv, {shell:false, cwd, env, stdio})` owns a **direct child**, not its descendants. Pass a purpose-built environment allowlist per process (including only needed PATH/HOME, network CA/proxy and scoped token variables); never spread `process.env` into CI/tool children. Track every child before awaiting it; capture bounded stdout/stderr, exit code and signal; propagate failures according to the gate's fail-soft/fail-closed contract. For network calls use an `AbortController`/deadline; aborting a fetch or sending a child signal does not itself kill spawned descendants. On Linux, use `detached:true` to start a separate process group; send `SIGTERM` to negative PGID, wait a bounded grace interval, then `SIGKILL` the group, await child `close` and retire the PID. The fixture demonstrates timeout + child/grandchild termination, but a descendant that creates a new session/group escapes that strategy; separately verify this against realistic command trees and cancellation/parent abnormal exit before replacing `gating.sh`. Reaping an adopted grandchild is the OS init's job, not something Node can `wait` for. Do not rely on GitHub runner's orphan cleanup (`RUNNER_TRACKING_ID`) as the action's ownership policy. Register `SIGTERM`/`SIGINT` handlers that cancel all active work and finalize within a bounded deadline; `finally` handles ordinary errors, while SIGKILL/power loss cannot run JS cleanup. If shell-level finalization is required after a CLI step failure, use an explicit `if: always()` composite step with only the necessary paths, not a second orchestration engine. A tiny external process-tree helper is only justified if negative-PGID cleanup proves insufficient in later integration testing; keep a fail-closed preflight rather than silently degrading to wrapper-only kill.

The domain layer should consume a `PlatformClient` interface for operations such as `getPullRequest`, `getComments`, `publishReview`; GitHub and Forgejo implementations own base URL, auth (GitHub bearer vs Forgejo token/OIDC JWT), pagination, payload normalization, and missing API capabilities. The fixture's injectable `getRepository`/`apiPath` is a narrow demonstration, not a production client. Read context from explicit runner env/event JSON, with validated repo/PR identity and platform URL selection; avoid `@actions/github`/Octokit in domain logic. `@actions/core` can be used at the runner edge for output, masking and summary once dependency review is done. Protect token-bearing request errors from logs and argv.

## Packaging and consequences

For #672: target **Node 22 LTS** for the composite CLI initially (the GitHub composite proof ran Node 22; native Node 24 also worked), compile TypeScript with `tsc` targeting ES2022, bundle via pinned `esbuild` into a single `dist/index.js` (plus any explicitly included static assets). Commit `dist/` so consumers install neither npm nor TypeScript; require a supported Node executable in the job image and check its major version in the launcher. Bundle production dependencies (Node built-ins and a few reviewed Actions libraries), lock exact dependency versions, review install scripts, and enforce a clean reproducible bundle rebuild in CI (`npm ci`, build, `git diff --exit-code -- dist`). Keep source maps out of the shipped artifact initially; enable local maps in development only and do not leak secrets in stack traces. This is a recommendation for #672, not a toolchain introduced by this spike; Node version policy must be rechecked against supported Forgejo images and security support before release.

For #671–#681: preserve public snake_case inputs/outputs until a separately planned migration, implement adapters and capability normalization before replacing `platform_api.sh`, port lifecycle/least-privilege gates before swapping the orchestrator, retain output/summary and failure semantics, and test both runner contracts (especially Forgejo) before any production cutover. #661's semantic-eval scorer and #662's reviewer dataflow remain independent. The fixture workflow is a manual/branch spike, not a production reviewer path; it neither changes `action.yml` nor invokes a model.
