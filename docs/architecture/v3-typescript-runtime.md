# ADR: v3 TypeScript runner boundary

Status: selected for the v3 migration (#670, parent #669). No production runtime change in this ticket.

## Current architecture

`action.yml -> composite steps -> Bash orchestration -> Python domain helpers`.
The manifest validates `gh`, `jq`, `curl`, `git`, `python3`, and `pgrep` before starting; serializes shared inputs into an owner-only file under `RUNNER_TEMP`; executes precheck, review, publish, and cleanup as separate composite steps. `scripts/run_review.sh` sources ordered sections, with `config.sh` setting defaults and `review.sh` writing `GITHUB_OUTPUT` and a best-effort `GITHUB_STEP_SUMMARY`. Review artifacts live in the checked-out workspace, while scripts are found through `github.action_path` / `GITHUB_ACTION_PATH`. `gating.sh` forks the CI and specialist branches, passes the CI subprocess an explicit `env -i` allowlist, walks the child tree with `pgrep -P` on abnormal exit, TERM/KILLs and waits for its leaders. This is required because killing the Bash wrapper alone has previously left network subprocesses alive. `platform_api.sh` routes host API calls to `gh` or `pr_reviewer/forgejo_backend.py` (`/api/v1`, PAT or runner OIDC JWT); GitHub-only GraphQL and Forgejo's missing check-runs API already have explicit degradation. Input/env serialization, state, traps, and platform differences are currently spread across shell, Python, and action metadata.

## Options and evidence

* **A: native JavaScript action**, `runs: {using: node24, main: dist/index.js}`. GitHub gives it a managed Node runtime and supports `post:` for post-job cleanup. Forgejo's [current action guide](https://forgejo.org/docs/latest/user/actions/actions/) documents `node20` actions, but does **not** establish `node24` support; Node actions also require Node in the runner's container image. A native-only v3 release would bet on an untested interpreter selector and lifecycle on Forgejo.
* **B: composite action with a one-step bundled Node CLI**. `shell: bash; run: node "$GITHUB_ACTION_PATH/dist/index.js"`, with `env` mapping kebab-case `inputs.*` to explicit CLI env names and `outputs.*.value` projecting step outputs. This is the contract used by production today, and [Forgejo's guide](https://forgejo.org/docs/latest/user/actions/actions/) documents composite actions and local action paths. The runtime still requires a suitable `node` executable in the job image; the wrapper must check it and fail with a useful version error. A composite's `if: always()` cleanup step can run after a failed main step, but it is not a substitute for in-process `finally` or signal/process-tree cleanup during a hard kill.

The isolated proof is `.github/workflows/v3-runtime-spike.yml` and `tests/fixtures/v3-runtime/`. **Real GitHub execution:** [workflow run 35883163488](https://github.com/misospace/pr-reviewer-action/actions/runs/35883163488), `ubuntu-latest`, 2026-09-23, checked-out commit `f1bbcb16c18b918413502a1f87623ba34c0ce2f7`. The job passed. Native `node24` (`v24.19.0`) and composite launcher (`node v22.23.2`) both read `test-kebab-input=kebab-value`, resolved bundled `marker.txt` and checked-out `GITHUB_WORKSPACE`, parsed `GITHUB_EVENT_PATH` and `GITHUB_REPOSITORY` (workflow_dispatch identity `misospace/pr-reviewer-action`), fetched that repository with the workflow token via `getRepository`, ran `git rev-parse --show-toplevel` via argv (exit/stdout/stderr checked), wrote `test-kebab-output` consumed by a later expression (`native-passed` / `composite-passed`), appended and read back a summary, and wrote finalization markers. Runner logs show `mask probe: ***` after registering a non-sensitive canary via `::add-mask::`; the actual token is also registered, never printed. For the hung `sh -c 'sleep 90 & ...; wait'`, process-group TERM returned control and the checked grandchild PID no longer existed on this run. Both failure probes intentionally threw; `steps.failure.outcome=failure`, `steps.native_failure.outcome=failure` and their separate finalization markers existed. These demonstrate JS `finally` on thrown errors, **not** post-job cleanup after forced cancellation. The fixture uses Node built-ins only and does not call any review/model endpoint.

**Forgejo runner qualification (#683): executed on a disposable harness.** `tests/forgejo_e2e_smoke.sh` (opt-in, `FORGEJO_E2E=true`, Docker required) starts a disposable Forgejo instance, runs the REST backend smoke, then registers an ephemeral `act_runner` (runner `v6.3.1`, job image `node:24-bullseye`, registration token via the server CLI — Forgejo 9 exposes no REST endpoint for it) and executes `tests/fixtures/forgejo/runner-compat/compat-workflow.yml`, which runs the retained #682 composite fixture as a local action inside a real Forgejo Actions job. Executed 2026-09-23 against `codeberg.org/forgejo/forgejo:9` on the #672 Node 24 baseline; the harness passed and its `PASS` line recorded the executed interpreter: **`node v24.20.0`** on `node:24-bullseye`. Executed and passing: composite local-action resolution (`uses: ./v3/composite`); node launcher preflight (`command -v node` plus a hard major-version check requiring **Node >= 24**, matching the #672 baseline); `GITHUB_ACTION_PATH` resolution (bundled `marker.txt` + `node "$GITHUB_ACTION_PATH/../cli-entry.mjs"`); kebab-case input mapping (`test-kebab-input=kebab-value`); output propagation via a later `steps.<id>.outputs.*` expression; event/repository aliases (`GITHUB_REPOSITORY`, push-event `GITHUB_EVENT_PATH` identity); `GITHUB_OUTPUT` write and read-back; step-summary write and read-back **within the emitting step**; secret masking (stored job log shows `mask probe: ***`, and neither the raw mask canary nor the raw token appears in the log); failure/finalization semantics (a deliberate throw still ran the JS finalizer, `continue-on-error` reported `outcome=failure`, and a later step asserted both finalization markers); and a Forgejo REST adapter request (`/api/v1/repos/...` with `Authorization: token`) against the disposable service. The runner exports the full `GITHUB_*` alias set (`GITHUB_API_URL`, `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `GITHUB_EVENT_PATH`, …). The harness pins these claims to automated assertions on the decompressed job log (launcher preflight line with the executed version, the propagated output value, the fixture's post-check summary line, the masked probe, the failure/finalizer evidence) before emitting `PASS` — nothing rests on narrative alone.

**Recorded Forgejo difference:** act_runner resets `GITHUB_STEP_SUMMARY` per step, unlike GitHub's job-wide accumulation — a later step cannot read an earlier step's summary content. The compat workflow asserts this, not just documents it: one step writes a canary into its summary file and the next step fails if the canary is visible in its own (fresh) summary file, so a runner that starts accumulating would fail the qualification loudly. Runtime requirement: step-summary handling stays in-step (write plus read-back in the same step), which is what the composite runtime already does. The job image must itself ship a suitable `node` and `git` (`node:24-bullseye` with `node v24.20.0` verified); the wrapper keeps its fail-closed launcher preflight requiring Node >= 24 rather than assuming them. Precision on what is and is not qualified: Forgejo's **native Actions `node24` selector remains unverified** and is irrelevant to the selected composite wrapper, which invokes `node` directly through a shell step; what the qualification now proves is the **availability of a Node 24 executable in the job environment** (and its discoverability via `PATH`/`node --version`). Still unverified: the authorized-integration OIDC JWT flow and forced-cancellation semantics — the same boundary as the GitHub evidence. The disposable instance (and its run ids) is destroyed after each harness run; the evidence above is reproducible by re-running the documented harness command.

## Decision

**Select B: composite compatibility wrapper + bundled Node CLI.** The real GitHub run proved both options, but Forgejo JavaScript-action `node24` support is not established. Composite is the already-working production runner contract and keeps the launcher trivial; TypeScript owns application orchestration, state, and domain logic. Native Node lost on cross-platform confidence, not GitHub functionality. Keep the action metadata composite until a separately evidenced cross-platform change.

## Lifecycle and platform boundary

Node `child_process.spawn(file, argv, {shell:false, cwd, env, stdio})` owns a **direct child**, not its descendants. Pass a purpose-built environment allowlist per process (including only needed PATH/HOME, network CA/proxy and scoped token variables); never spread `process.env` into CI/tool children. Track every child before awaiting it; capture bounded stdout/stderr, exit code and signal; propagate failures according to the gate's fail-soft/fail-closed contract. For network calls use an `AbortController`/deadline; aborting a fetch or sending a child signal does not itself kill spawned descendants. The demonstrated negative-PGID strategy is **POSIX/Linux**: use `detached:true` to start a separate process group; send `SIGTERM` to negative PGID, wait a bounded grace interval, then `SIGKILL` the group, await child `close` and retire the PID. The fixture demonstrates timeout + child/grandchild termination on Linux; **Windows descendant cleanup was not demonstrated**. Forced cancellation and descendants escaping their process group remain explicit requirements for #679; verify them against realistic command trees and parent abnormal exit before replacing `gating.sh`. Reaping an adopted grandchild is the OS init's job, not something Node can `wait` for. Do not rely on GitHub runner's orphan cleanup (`RUNNER_TRACKING_ID`) as the action's ownership policy. Register `SIGTERM`/`SIGINT` handlers that cancel all active work and finalize within a bounded deadline; `finally` handles ordinary errors, while SIGKILL/power loss cannot run JS cleanup. If shell-level finalization is required after a CLI step failure, use an explicit `if: always()` composite step with only the necessary paths, not a second orchestration engine. A tiny external process-tree helper is only justified if negative-PGID cleanup proves insufficient in later integration testing; keep a fail-closed preflight rather than silently degrading to wrapper-only kill.

The domain layer should consume a `PlatformClient` interface for operations such as `getPullRequest`, `getComments`, `publishReview`; GitHub and Forgejo implementations own base URL, auth (GitHub bearer vs Forgejo token/OIDC JWT), pagination, payload normalization, and missing API capabilities. The fixture's injectable `getRepository`/`apiPath` is a narrow demonstration, not a production client. Production base-URL/platform validation belongs to the platform adapter work in #674, not this spike. Read context from explicit runner env/event JSON, with validated repo/PR identity and platform URL selection; avoid `@actions/github`/Octokit in domain logic. `@actions/core` can be used at the runner edge for output, masking and summary once dependency review is done. Protect token-bearing request errors from logs and argv.

## Packaging and consequences

For #672: target **Node 24 LTS** for the composite CLI (the baseline #672 sets; the Forgejo qualification ran `node:24-bullseye` with `node v24.20.0` and the launcher preflight requires Node >= 24), compile TypeScript with `tsc` targeting ES2022, bundle via pinned `esbuild` into a single `dist/index.js` (plus any explicitly included static assets). Commit `dist/` so consumers install neither npm nor TypeScript; require a supported Node executable in the job image and check its major version in the launcher. Bundle production dependencies (Node built-ins and a few reviewed Actions libraries), lock exact dependency versions, review install scripts, and enforce a clean reproducible bundle rebuild in CI (`npm ci`, build, `git diff --exit-code -- dist`). Keep source maps out of the shipped artifact initially; enable local maps in development only and do not leak secrets in stack traces. This is a recommendation for #672, not a toolchain introduced by this spike; keep the policy aligned with the Node LTS schedule and supported Forgejo job images before release.

For #671–#681: the v3 public contract is **kebab-case** (#671, canonical in `contracts/action-v3.yml`); the root `action.yml` stays v2 (snake_case) only until the atomic cutover in #681, so no snake_case-compatibility shims are carried into v3. Implement adapters and capability normalization before replacing `platform_api.sh`, port lifecycle/least-privilege gates before swapping the orchestrator, retain output/summary and failure semantics, and test both runner contracts before any production cutover (the composite contract is now Forgejo-executed via #683 on the Node 24 baseline). #661's semantic-eval scorer and #662's reviewer dataflow remain independent. The fixture workflow is a manual/branch spike, not a production reviewer path; it neither changes `action.yml` nor invokes a model.
