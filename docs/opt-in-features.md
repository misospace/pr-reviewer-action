# Opt-in features

The features below default to `false`. None change the verdict policy on their own; each adds context or coverage the final reviewer can use, and fails soft on error.

## `claim-falsification`

**What it does:** scans the PR's own description and its diff's added comments/docstrings for quantified claims and invariants the PR author made — "only", "never", "always", "byte-identical", "all callers", "cross-checked", authority boundaries, compatibility promises — and anchors each to the concrete function or line it describes (never a whole file). Comment blocks are joined and split into whole sentences (never per-line fragments), bot-authored body boilerplate (Renovate/Dependabot footers) is skipped, PR-body claims always outrank diff-comment claims, and each claim enumerates the items it quantifies over when they are resolvable from the diff (every inline identifier plus flag-like tokens such as `repo-configurable`, so a claim over "every input carrying the flag" ships the flagged lines; a line whose only symbol is git's hunk-header guess still counts, anchored as `file:L<n>`). One bounded model call on the primary route (`src/claims/model.ts`) then runs when a primary route exists and merges its claims after the deterministic ones — the scan is evidence, never proof the body was fully captured, and a model failure keeps the scan's claims. On a dependency-update PR (#1380, keyed to the normalized dependency-update classification, never a bot identity), machine-generated dependency metadata — exact old→new version/tag pairs, digest presence/absence, changed-file/manifest counts, automerge/branch-scheduling/rebase boilerplate — is filtered before the model pass: a mixed sentence keeps only its semantic clauses ("Only one file changed; the CRD schema is unchanged" still yields the CRD claim), and the model call is skipped entirely (status `filtered`) only when the filter actually scanned content and dropped every sentence as metadata — vendor-agnostic update-list/generator scaffolding lines ("This PR contains the following updates:") included — because a remaining non-metadata sentence keeps the model pass even when the keyword scan found no candidate ("No migration required" carries no keyword vocabulary yet is a real falsification target), an unscanned body (bodyless PR, code-only diff) gives the filter nothing to account for, and text swallowed by an unclosed `<!--` counts as unseen content, not as proven metadata; when the model pass runs, its dependency-metadata-only output is post-filtered the same way; vendor-name boilerplate matching is never used in dependency mode — a sentence that merely mentions Renovate or Dependabot keeps its semantic claim, boilerplate is dropped by vocabulary shape only, and a sentence whose subject merely shares wording with boilerplate ("The rebase-check workflow is unchanged") keeps its claim. On a dependency update the pre-pass also launches only after the evidence phase has settled, so the mandatory dependency-evidence obligations keep budget priority over optional claim-falsification work. The review corpus then gets a `# Claims to Falsify` section telling the reviewer to check every listed claim (plus any the list missed) and report a counterexample as a finding.

**Enable:** `claim-falsification: true`.

**Artifacts and knobs:**

| Name | Default | Notes |
| --- | --- | --- |
| `claim-falsification.json` / `claim-falsification.md` | — | Per-run artifacts |
| `CLAIM_FALSIFICATION_MAX_TOKENS` (env) | `4096` | Model-fallback completion budget |
| `CLAIM_FALSIFICATION_TIMEOUT_SEC` (env) | `180` | Capped by `ai-request-timeout-sec` |
| `CLAIM_FALSIFICATION_INPUT_MAX_BYTES` (env) | `48000` | Model-fallback input cap |
| `CLAIMS_SECTION_MAX_BYTES` (env) | `8000` | Corpus section cap |

**Status:** default off, experimental. Pre-release it was measured only together with `requirement-trace` and `equivalent-paths` (all three on vs. off, blind-adjudicated), which showed no net gain as a bundle. A small three-PR smoke on its own found one extra catch with one model and none with two others; that smoke also exposed the extraction defects #898 fixed (line fragments, crowded-out body claims, unenumerated quantified items, bot boilerplate). The smoke is to be re-run before the feature is measured again.

## `derived-obligations`

**What it does:** one bounded model call on the primary route, over the PR's complete diff (then the pass's own bounded clipping — never the prioritized context slice, which can omit the hunk that raises the obligation), changed files, title and body (all untrusted data), derives from the change itself the cross-path obligations it implies even when the PR never states them — identity/dedupe keys, converging producers, routing keys, persistence/recovery, retry/reconciliation/fallback, trust boundaries, ordering, compatibility — at most 4 structured obligations, each with its topology class, the change that raises it, the relationship that must hold, concrete `path:symbol` locations to check, and its provenance basis. Bounds are enforced by normalization, not by trusting the model: an unknown topology class normalizes, and oversize fields/paths are truncated with visible flags. The review corpus then gets a `Derived Architectural Obligations` section the reviewer must disposition each entry against, and a derivation that failed, timed out, returned malformed output, or ran over an incomplete diff view renders a short visible "coverage unavailable" note in the section instead of silence; the per-run JSON artifact records the status, error kind, and input completeness (`diff_source`, `diff_clipped`, `input_complete`) so the enforcement half can distinguish "no obligations" from "derivation incomplete" and from "the derivation never saw the relevant change". When no obligations derive cleanly over a complete input the corpus is byte-identical to a disabled run.

**Enforcement (#1449):** the derived obligations are review-owned obligation rows in the authoritative review-coverage/enforcement path, not presentation any more. Every row carries an id (`derived-<n>`) the reviewer echoes in `required_check_dispositions`, and a `satisfied` row's rationale must name one of the derivation's own locations — the evidence must reach the flagged site, because a callback receiving a value is not the production site placing it. The rows are listed to the reviewer where the reviewer acts: the corpus section, the tool harness's required-evidence planning section, and the review call's steering block. An unresolved derived obligation withholds a trusted approve and is reported as incomplete coverage in its own section — never as a fabricated blocker finding, because an unresolved obligation is a coverage statement, not a defect claim; a counterexample the reviewer actually found is reported as an ordinary evidence-backed finding under the normal findings rules. A derivation that did not complete withholds the trusted approve too: the derived-obligation coverage is unavailable, and one synthetic coverage-marker row holds the approval back until the derivation ran. The gap is disclosed, not downgraded: the run's `review_result` reads `partial` (never `clean`, and never a manufactured `issues`), and the state is published as `unavailable` with the derivation's own failure reason — the coverage marker never becomes a synthesized blocker finding and never re-labels itself as a failed check. The withholding is an ABSTENTION, not a block: a derived row never forces a `request_changes` verdict and never publishes a blocking native request, because an incomplete review must not manufacture an issue (#1447 keeps the distinction between a found defect and a review that is incomplete). The native review event is a `COMMENT` with an explicit "approval withheld by derived-obligation state" note — exactly like the fork/scope guardrail's withhold. The run's `review-coverage.json` record and the metadata marker disclose the state (`complete`, `unresolved`, or `unavailable`) together with the closed reason that explains it (`not-discharged` when the coverage is complete but a derived obligation stayed open, the derivation's own failure reason when the coverage is unavailable), so a reader can tell that an approval was withheld because a derived architectural obligation stayed unresolved. A derived obligation is discharged only by evidence that names one of the derivation's listed locations — an anchor that does not look like a location is not one, and a derivation that listed none is discharged by a rationale naming a path-like token, so the review can never be bricked by an unusable derivation.

**Enable:** `derived-obligations: true` (workflow input only — not repository-configurable). The feature stays operator-only: it can withhold a trusted approve, so it must never be switchable from repository-controlled config.

**Artifacts and knobs:**

| Name | Default | Notes |
| --- | --- | --- |
| `derived-obligations.json` / `derived-obligations.md` | — | Per-run artifacts |
| `derived-obligation-state.json` | — | Per-run enforcement state (coverage, reason, rows) |
| `DERIVED_OBLIGATIONS_MAX_TOKENS` (env) | `4096` | Derivation-call completion budget |
| `DERIVED_OBLIGATIONS_TIMEOUT_SEC` (env) | `180` | Capped by `ai-request-timeout-sec` |
| `DERIVED_OBLIGATIONS_INPUT_MAX_BYTES` (env) | `48000` | Derivation-call input cap |
| `DERIVED_OBLIGATIONS_SECTION_MAX_BYTES` (env) | `8000` | Corpus section cap |

**Status:** default off, experimental; the derived obligations now take part in the authoritative coverage/enforcement path (#1449) — an unresolved one withholds a trusted approve and is reported as incomplete coverage.

## `risk-obligations`

**What it does:** a deterministic, model-free scan (`src/risk/classify.ts`) over the PR's complete diff raises one evidence obligation per risk category the CHANGED CODE itself touches: file identity/path mode, bounded state/counters/concurrency, persisted state, and credential/security boundaries. The first target case is mode-aware file identity: a `git ls-tree` blob-equality proof cannot distinguish regular-file mode 100644/100755 from symlink mode 120000 (the symlink blob stores only its target pathname), so changed tree-parsing/mode-handling code — and real mode flips (`old mode 100644` → `new mode 120000`) — must be met with the symlink counterexample. Like the #749 classification discipline, only changed lines of code files count: docs, lockfiles, vendor output and mentions that survive only inside a recognized comment never fire. The obligation statements are closed static text naming the counterexample class and the source/test evidence that discharges it; the triggering paths ride as anchors. The review corpus gets a `Risk Evidence Obligations` section and the review call's steering block lists the rows.

**Enforcement:** the risk obligations join the same review-owned obligation contract as derived rows (#1381/#1449 semantics): each row (`risk-<n>`) is echoed in `required_check_dispositions`, and a `satisfied` row's rationale must name one of the flagged locations (a `satisfied` rationale that asserts failure keeps the row open). An unverified risk obligation withholds a trusted approve and marks the review `partial` with its own disclosure section — never a fabricated blocker finding, and a risk row never forces `request_changes`; a real counterexample is reported as an ordinary evidence-backed finding. A scan that did not run over the complete diff leaves risk coverage unknown: one synthetic `risk-coverage` row (cause `scan-incomplete`, never dischargeable by a disposition) withholds the approval the same way.

**Enable:** `risk-obligations: true` (workflow input only — not repository-configurable; it can withhold a trusted approve, so it stays operator-only). No model call is added and no tool budget changes. The rows reach the reviewer through the corpus section and the steering block, and a row is discharged only through `required_check_dispositions`. Unlike derived rows (#1449), risk rows are not wired into the tool harness: `src/tools/harness.ts` reads only `derived-obligations.json`, so risk anchors are not part of the required-evidence planning section or the enforced-window admission vocabulary.

**Artifacts:**

| Name | Default | Notes |
| --- | --- | --- |
| `risk-obligations.json` / `risk-obligations.md` | — | Per-run scan artifacts (both written only when the scan is enabled) |
| `RISK_OBLIGATIONS_SECTION_MAX_BYTES` (env) | `8000` | Corpus section cap |

**Status:** default off; deterministic scan, model-free by construction (#1577).

## `requirement-trace`

**What it does:** for every acceptance/normative requirement **in trace scope**, requires the model to additionally cite both the production code that enforces it and the regression test that would fail if that enforcement broke (`src/enforcement/requirement-trace.ts`). Each citation is deterministically checked against the actual checkout at head — not trusted from the model's say-so — and the cited enforcement location must contain a real predicate (a comparison, guard, assertion, or match), not just an assignment. For a prose standard whose enforcing code never spells the requirement's own wording, the lexical half of that check is replaced by the base-ref-trusted owner declaration: a citation into a file declared an owner of that requirement in `.github/pr-reviewer-owners.yml` needs only a real predicate, on the cited line itself (design note: `docs/architecture/owner-anchored-enforcement-citation.md`). A requirement with a missing or unverifiable trace is marked `unverifiable`, and a well-formed `unmet` requirement with no corresponding finding gets a deterministic one; either folds into `required-checks=incomplete`. Trace scope (#935) is deterministic: linked-issue requirements (what the PR was asked to deliver), any requirement whose subject the change touches, and entries without provenance. Subject overlap (#957) needs strong evidence — a multi-word phrase from the requirement, a single identifier-shaped term (a digit-bearing token like `sha256`, or an internal capital like `sourceSha`/`SQLite`), or a changed file declared as an owner of the requirement in `.github/pr-reviewer-owners.yml` (#958) — in the changed files or lines of the full diff, not the budgeted one; two plain generic words (`docs`, `repo`, `request`, `only`, `never`, …) and bare acronyms (`PR`, `API`, `URLs`) are never enough on their own. A phrase counts only when at least one of its two words is specific (#1346): a pair of pure connectives — `only through`, `never appear`, `may appear` — occurs in the ordinary prose comments of any diff and names no subject, while a mixed pair like `data never` still counts, because `data` does.

Boundary ownership (#958) is explicit architectural metadata, not inferred from prose: `.github/pr-reviewer-owners.yml` (read from the PR's base ref, like the repository config) maps a named security boundary to the production/enforcement files that own it, so a change to `.github/workflows/ai-pr-review-fork.yaml` keeps the fork-privilege standard in scope even though ordinary workflow edits repeat none of its prose. The key is a slug whose 3+ char tokens must all appear in the requirement text; owner paths are exact files or narrow globs (`**`, absolute paths, and `..` are rejected). A malformed or missing file degrades to "no owners" with a warning and never broadens scope. If the raw diff is unavailable, every requirement stays in scope. Other standards / PR-body / harness requirements are dispositioned `not_applicable` with an "out of scope" reason and never make coverage incomplete on their own (the reviewer can still report one `unmet`). The prompt asks the model to trace only the in-scope requirements, by id.

**Non-code proof domains (#1062):** not every acceptance criterion is a code/test-verifiable obligation, and demanding a runtime predicate plus a regression test from one falsely withholds approval. PR #1060 is the motivating false block: a Python-test-cleanup PR was held at a partial result with 9 of 11 trace rows `unverifiable`, because its linked-issue criteria also included an inventory to record in the PR description, the preservation of external workflow / CI green state, and whether an unrelated pull request would merge in the future — none of which a unit test can observe. The validator classifies each in-scope row deterministically from the ledger requirement text — **never from a model field**, so the model can never authorise itself out of a mandatory code proof — into one of two non-code domains, and dispositions it accordingly:

- `external_state` — a completed-CI / external-workflow / future-or-other-PR-merge outcome that no checkout predicate can observe. The row is dispositioned `pending`: a non-blocking advisory surfaced in its own "Non-code criteria" section, never folded into `required-checks=incomplete`, and never `met` (the outcome is surfaced, not certified). Each advisory names its requirement's **provenance and scope basis** (e.g. "from the linked issue, unconditionally in scope") and, for an external-state row, the **known exact-head CI state** from this run's CI gate — or explicitly that none was observed — so the author can see what the review could and could not check.
- `documentation` — a recording obligation aimed at a **named documentation/metadata artifact**, confirmed ONLY from that artifact's own trusted source: a PR-description/PR-body target is `met` when a single quoted literal is positively present in the trusted PR body; a README/CHANGELOG/docs target is `met` only when the literal is found in the matching file of the **exact-head checkout** (root `README*`/`CHANGELOG*`, root docs files, and the `docs/` tree, under a bounded scan that never follows symlinks). The PR body describing `X` is never proof that the README contains `X`, and a target naming both sources (or a docstring, which has no bounded file source) stays `pending`. Neither case is ever verified by inventing a source-code predicate.

What a `pending` row means, precisely: the criterion is reported to the author but **does not block approval**. What still blocks, unchanged: any genuine code-behaviour requirement, any distributed enforcement seam, any structural-state verification, any mandatory regression/security test, and any well-formed `unmet` — including a bare `unmet` with no reason on a non-code row, which degrades to blocking `unverifiable` just as it does for a code requirement. Any requirement carrying a code-action, enforcement, **or publish/report/ship/release** verb (`compare`, `validate`, `authenticate`, `redact`, `report a status check`, `ship the release`, …), naming a source or test path, or demanding test coverage is vetoed out of the non-code domain and stays on the strict `unverifiable`-blocks path. The `external_state` domain also requires the criterion to name its dependency as **explicitly external/unrelated** (e.g. "external CI checks", "unrelated pull request #1052") — a bare `CI`/`PR #N` mention is not enough, so the product's own CI/PR requirements stay enforced. And a `documentation` row is confirmed only against a named documentation/metadata target (PR description, README, …), never from a bare "record/document" verb. So an ambiguous or hostile criterion keeps its teeth.

**Enable:** `requirement-trace: true`.

Note: this depends on a bundled prompt fragment that asks the model to emit the trace fields (`enforcement`/`test`/`disposition`). A `replace`-mode `system-prompt` that doesn't emit them fails closed — every in-scope requirement becomes `unverifiable` and coverage `incomplete`, which is safe but easy to be surprised by.

**Blocking findings require a substantiated violation (#1095):** the enforcement pass never synthesizes a finding from an `unmet` row. The model's prompt contract obliges it to file the matching finding itself; fabricating a blocking major from the ledger text alone let process dependencies and PR risk notes that leaked into the ledger hold a defect-free refactor at CHANGES_REQUESTED (miso-gallery#543, review 5549785027: three "requirement not enforced" majors, zero code defects, model verdict approve). An `unmet` the model substantiated with its own finding still blocks through that finding; an unsubstantiated one keeps `required-checks=incomplete` — no clean approval — and is disclosed in the rendered trace section instead. Two companion guards close the promotion path at its source: the ledger extractor skips **advisory/process sections** (headings like `Dependencies`, `Notes`, `Risk`, `Caveats`, `Rollout` — exact normalized match), so a merge-order note or a maintenance caveat never becomes a requirement; and the `external_state` domain additionally recognizes a **test-execution outcome** ("`tests/…py` pass with only import-path updates") — whether tests pass is observable only by running them, so the row pends as a non-blocking advisory while the run's CI gate state is surfaced in its notes. The code-verb veto and every other fail-closed guard are unchanged.

**Distributed enforcement (#962):** a cross-cutting standard is often enforced across several seams, so a single enforcement location plus a single test cannot honestly prove it. `.github/pr-reviewer-owners.yml` may declare a rule's `groups` — named seams, each with its own narrow owner globs and test globs — and requirement-trace then requires the model's citations to cover **every** declared seam with a distinct enforcement location **and** a distinct matching test (a maximum bipartite matching, so one citation can never cover two groups). Because every seam must declare a test surface, an unrelated generic test file cannot satisfy a distributed requirement. Topology is base-ref-trusted config, never model output: a payload cannot promote a requirement to distributed, extra citations that miss every declared seam glob contribute nothing, and declaring more seams than the bounded cap can represent fails the trace closed rather than validating a truncated proof. The distributed predicate check is predicate-only — no term derived from the requirement text is consulted, and the model-supplied `symbol` is ignored — so a value-copying seam cannot be laundered with a term the model invented. A distributed requirement's uncovered seams render by name. The pinned contract is [`architecture/distributed-requirement-proof.md`](architecture/distributed-requirement-proof.md).

**Missing claims (#959):** a verdict that carries no trace claim at all for an in-scope requirement is not the same failure as a claim whose cited location is unusable, and the two no longer render alike. Before publishing, one bounded repair pass (`src/requirements/trace-repair.ts`) re-asks the producing route for the unresolved ids — since #1552 that is the ids with no claim AND the ids whose validator row is still `unverifiable` (the present-but-unverified shape) — and merges any claims it returns through `mergeTraceRepairClaims`: ids with no row are appended, and inside the validator-derived target set a row the validator left `unverifiable` is replaced in place (a stored `unmet` row is never replaced, and ids outside the target set are never touched, so a claim with bad locations that stays unverifiable still fails closed). Since #1044, a row with no claim renders differently depending on whether the pass ran for it: an id the pass ran for and did not fill renders "the reviewer reported no trace for this requirement, and a bounded repair pass also returned no usable claim", while an id the pass never targeted keeps the plain wording. The run artifact carries a bounded summary of the pass outcome (`requirement_trace_repair`: outcome, post-merge `missing_ids`, claim count, rows the merge actually changed, targeted rows' pre-repair repair states, sanitized diagnostics); any error text in it is credential-masked and pattern-redacted before persistence, and the rendered markdown stays static text — error/status details never reach it. The pass is gated on the default prompt (an operator `replace`-mode prompt has no fragment to retry, so it stays fail-closed) and is fail-soft: a transport error, timeout, or malformed reply leaves the artifact unchanged.

**Knobs:**

| Name | Default | Notes |
| --- | --- | --- |
| `REQUIREMENT_TRACE_REPAIR_MAX_TOKENS` (env) | `4096` | Repair-pass completion budget |
| `REQUIREMENT_TRACE_REPAIR_TIMEOUT_SEC` (env) | `180` | Capped by `ai-request-timeout-sec` |
| `REQUIREMENT_TRACE_REPAIR_INPUT_MAX_BYTES` (env) | `48000` | Repair-pass input cap |

**Status:** default off, experimental. Measured only as part of the three-feature bundle described under `claim-falsification`, which showed no net gain; not yet measured on its own.

## `equivalent-paths`

**What it does:** a bounded, deterministic (no model) detector over the diff's already-extracted change anchors (`src/context/equivalent-paths.ts`). It groups changed functions/methods that look like alternate routes to the same result — matching return type, matching constructed object shape, a shared method name across sibling `*Adapter`/`*Provider`/`*Client` classes, or calls to the same privileged operation — and gives the `correctness` specialist a compact "Equivalent Paths to Compare" hint (`file:line` per member) so it checks sibling paths for the same invariants. It never claims an asymmetry exists on its own; it only points at paths worth checking. The motivating case (#854): one path checked a repo-identity match and a sibling path returning the same object type didn't.

**Enable:** `equivalent-paths: true`.

**Artifacts and knobs:** `equivalent-paths-max-bytes` (default `6000`) caps the section's size in the specialist corpus; capped at `MAX_GROUPS = 3` groups of up to `MAX_MEMBERS_PER_GROUP = 4` members each.

**Status:** default off, experimental. Measured only as part of the three-feature bundle described under `claim-falsification`, which showed no net gain; not yet measured on its own.

## `harness-obligations`

**What it does:** derives deterministic verification questions from context the pipeline already resolved — related-code call sites and change anchors (`src/requirements/obligations.ts`) — and injects them into the requirement ledger as ordinary entries, ordered most-connected-caller-first. The reviewer answers them through the existing `requirement_coverage` contract like any other ledger entry; deterministic extraction (standards, linked issues, PR body) always outranks them, and they're the first entries the ledger cap drops.

**Enable:** `harness-obligations: true`.

**Artifacts and knobs:** no dedicated artifact file — obligations are ledger entries, visible in the requirement ledger section of the review corpus like any other requirement.

**Status:** default off, and this is the one with an actual measurement. A 37-PR blind-adjudicated A/B (`evals/reports/harness-obligations/`, #796/#841) ran the obligations on vs. off, labelled every finding against the human-identified defect and every blocker/major non-catch as real or false-positive with arms stripped before labelling, then unblinded. Conclusion: no recall gain and no false-positive improvement — the default stays off.

## Summary

All four are off by default because no measurement has shown them to help as a default: `harness-obligations` has its own blind-adjudicated A/B, and the other three were measured only as a bundle. They're safe to try (each is fail-soft and leaves the verdict policy alone), but treat them as experiments.
