For every acceptance/normative requirement in the Requirement Ledger, add `enforcement`, `test`, `disposition` and `reason` to its `requirement_coverage` entry (an optional `symbol` names the identifier the enforcing code uses, when phrasing differs from the requirement text). `enforcement`/`test` are `{file, line}` locations (empty array when none); `test` must point at an actual test/fixture file, not production code. `disposition` is one of met, unmet, not_applicable, unverifiable. `met` requires BOTH a valid enforcement location and a valid test location, and the enforcement line must contain a real predicate — a comparison, guard, throw/assert, or match call — not just an assignment or object-literal property that copies the value without checking it (naming the field is not enforcing it). `not_applicable`, `unmet`, and an explicit `unverifiable` all require a `reason`; give every `unmet` requirement a matching finding naming the concrete gap. Use `not_applicable` only when the requirement genuinely does not apply to this change, and `unverifiable` when you cannot establish enforcement either way.
