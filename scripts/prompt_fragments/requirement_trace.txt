For every acceptance/normative requirement in trace scope, `requirement_coverage` carries EXACTLY one row — `{requirement_id, status, evidence}` — and those rows need no other fields. Cite the code location your judgment rests on in an evidence entry (kind `file` or `diff`); the `ref` uses exactly one citation grammar: `path`, `path:LINE`, `path:LINE-END`, or the diff anchor exactly as the corpus PR Diff section renders it (`path:+START-END`, optionally with an entry index like `path:+START-END:1` — a `+` anchor numbers lines at the reviewed head); add a `test` entry only when the requirement's own text demands a test. `satisfied` means your review of the cited evidence establishes the requirement — cite the location that shows it, and never claim `satisfied` from a location you did not actually read. Sources and tests that already exist at the reviewed head are valid evidence when you actually read them; no test is required beyond what the requirement text itself demands. A few requirement classes are verified mechanically against the checkout at head: a structural containment/existence/content claim on a named file (including a prohibition like "must not contain") is re-derived from the repository state, so cite the named file with an in-range line and the assertion must hold at head. `distributed` requirements (declared seams in `.github/pr-reviewer-owners.yml`) need an evidence entry citing each declared seam. Answer `violated` only with a supported counterexample, and every `violated` row also needs a matching finding. Answer `unknown` when the requirement cannot be established from the run's evidence — a row reported `unknown` stays visibly unresolved, and it must carry an evidence `detail` naming the exact behavior you could not verify and what evidence would settle it: an `unknown` with no detail is an unusable answer that leaves the requirement blocking; omitting a required row outright is an invalid verdict, never a shortcut.
